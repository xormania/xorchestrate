**Location.** Deliverables sit at `ops/devlane/workflow/contracts/`, per SPEC
section 4 ("All deliverables live under `ops/devlane/workflow/contracts/`") — the

`vet.py`'s `HERE`/`APP_ROOT` pair, which is derived from `__file__`.

**Nothing of the module is imported or executed.** `.sql` goes through

the *copy* is opened `mode=ro`, `.json` goes through `json.loads`, and the
directory walk touches `os.walk`/`os.path` only.  No `.py` file of the app is
read by any of these five extractors.

## GUESS ledger, SPEC 5.1–5.5

SPEC marks two lines **GUESS** in 5.1–5.5.  Both are recorded below.  The
unmarked assumptions each shape carries are recorded after them, because a
reader checking this ledger against the shape spec should not have to
re-derive which sentences were load-bearing.

### The two marked GUESSes

**5.2 — `schema_migrations: [string]  # whatever the version/name column holds,
sorted — GUESS: column name unknown` → ADAPTED.**

The table has four columns: `version INTEGER PRIMARY KEY`, `name TEXT NOT
NULL`, `sha256 TEXT NOT NULL`, `applied_at TEXT NOT NULL`.  So both candidate
columns exist and the GUESS's premise ("unknown") is resolved, but the shape
does not say which to emit.  The extractor takes **`name`**, because `name`
holds `0001_foundation.sql` — the same string 5.1's `migrations` list holds,
which makes the two observations comparable.  The road not taken is not
hidden: `provenance.facts.schema_migrations` carries `column_used`,
`columns_available`, and `all_column_values` for every column, so a contract
written against `version` (`["1"]`) mismatches loudly and the evidence for the
other reading is one field away.  `applied_at`'s value is replaced with an
elision marker in provenance — SPEC section 4 forbids timestamps in
observations, and this one is a timestamp.

**5.5 — `gitignore: [...] — GUESS: where the ignore rule lives` → INFEASIBLE
in this snapshot.**

There is no `.gitignore` at the repo root and none anywhere under `.dev/`.
There is no `.git` directory either, so "repo root" was resolved by falling
back to the parent of the `.dev/` component of the app path; the method used
is recorded verbatim in `provenance.repo_root_determined_by`, and every path
searched is listed in `provenance.gitignore_files_searched` (empty here).
The fact is therefore `{"unresolved": ...}`, not `[]`.  The distinction is the
whole point and the extractor implements both halves of it:

* at least one `.gitignore` exists and no line of it contains `db` → `[]`, a
  real observation, with the files that were read named in provenance;
* no `.gitignore` exists in the searched scope → `{"unresolved": ...}`,
  because "no rule found" and "nowhere to look" are different answers.

`wf.db` **is** present in `facts.files`.  A contract that reads section 8/D1 as
requiring a matching ignore line will mismatch against the unresolved value.
That mismatch is real: in this tree the ignore rule genuinely does not exist
where 5.5 says to look for it.

## Readings taken where the shape left room

These are places where 5.1–5.5 admits more than one output and the extractor
had to choose.  Each is written here so a disagreement with the contract is
attributable to a choice, not to an accident.

1. **`primary_key` is sorted alphabetically, not in PK-ordinal order.**  5.1
   marks `columns` "declaration order" explicitly and marks `primary_key`
   nothing, and section 4 says "sorted lists only (determinism)".  So sorted.
   For `events` that means `["seq","wo_id"]` while the declaration is
   `PRIMARY KEY (wo_id, seq)`; `provenance.facts["tables[events].primary_key"]
   .declaration_order` in `schema` and
   `provenance.facts["tables[events]"].primary_key_declaration_order` in `db`
   both carry `["wo_id","seq"]`.  `schema.py` and `db.py` apply this reading
   identically — during development they did not, and the `schema`/`db`
   cross-check in finding 4 below is what caught it.
2. **`gatekinds.facts.kinds[].file` is `gate-kinds/tdd.json`, not `tdd.json`.**
   Section 4 defines a file path in this project as "path relative to
   `ops/devlane/workflow`"; the fact follows that convention rather than
   inventing a bare-basename one.
3. **`schema.facts.migrations` lists every regular file under `migrations/`,
   not only `*.sql`.**  5.1 says "filenames under migrations/", which is
   broader than what gets loaded.  `provenance.migrations_loaded` and
   `provenance.migrations_not_loaded` split the two.  Here they coincide: one
   file, loaded.
4. **Digests over JSON are UTF-8 encoded before hashing** (`json.dumps(...)
   .encode("utf-8")`).  The canonical form is exactly the one 5.2 gives:
   `json.dumps(obj, sort_keys=True, separators=(",",":"))`, `ensure_ascii` left
   at its default.
5. **Observation files are written with `ensure_ascii=False`, `indent=2`,
   `sort_keys=False`, LF endings, one trailing newline.**  Verbatim source
   text keeps its em dashes and section signs instead of turning into `—`
   escapes, which matters because section 4 says the adjudicator reads the
   code through the `text` field.
6. **Timestamps are elided from provenance, not just from facts.**  Section 4
   bans timestamps from observations; `schema_migrations.applied_at` and
   anything else matching an ISO-8601 prefix is replaced with a marker naming
   the rule.  The `synced_at` column of `gate_kinds` is not emitted at all —
   the 5.2 shape does not ask for it.
7. **Provenance is per fact, not per file.**  `obs/schema.json` carries 85
   provenance entries (one per table, one per column, one per primary key),
   `obs/layout.json` 56 (one per file and per directory).  The verbatim `text`
   for a column is its own declaration line; for a table, the whole `CREATE
   TABLE` block with its leading comments trimmed off so the line range starts
   at the keyword.

## What the shape spec does not fit

Recorded as observations, not fixed.  SCOPE: "A wrong implementation is
recorded as a finding, not fixed here."

1. **The database's `tdd` registry row has drifted from `gate-kinds/tdd.json`.**
   The file's `test_scope` is three globs:

   ```
   "crates/*/tests/**", "crates/*/src/**/*_test.rs", "ops/design/features/**"
   ```

   The `spec_json` stored in `gate_kinds` has only the first two — it is
   missing `ops/design/features/**`.  Canonical digests:

   | kind | file (`obs/gatekinds.json`) | db (`obs/db.json`) | agree |
   |------|------------------------------|--------------------|-------|
   | `artifact` | `dbbf262a3ea2b595…` | `dbbf262a3ea2b595…` | yes |
   | `tdd` | `495984ff1dbe2238…` | `353af4a52c010514…` | **no** |

   Any contract that requires the DB registry to equal the tracked files (5.2
   points at PLAN section 6 lines 328–331 for exactly this) will fail on
   `tdd` and pass on `artifact`.  The extractor emits both digests and takes
   no position; the two shapes were built to make this comparison possible and
   it comes out negative.

2. **Only the *canonical* digests are comparable across the two observations.**
   The stored `spec_json` bytes are already canonical (`raw == canonical` for
   both DB rows), while the tracked files are pretty-printed with newlines and
   two-space indent (`raw != canonical` for both files).  So
   `db.gate_kinds[].spec_sha256_raw` equals `gatekinds.kinds[].sha256_raw` for
   **neither** kind — including `artifact`, where the underlying objects are
   identical.  A contract that cross-checks the `_raw` pair will report a
   mismatch that is an artifact of formatting, not of drift.  5.2 says which
   digest is "the" `spec_sha256` is not stated in PLAN.md and leaves the pick
   to the contract author; this is the concrete reason the pick matters.
   `provenance…stored_bytes_are_already_canonical` records it per row.

3. **`pk: true` with `notnull: false` on seven of nine tables.**  `PRAGMA
   table_info` reports `notnull=0` for a column declared `<name> TEXT PRIMARY
   KEY` — and for TEXT primary keys SQLite really does permit NULL, so this is
   not a reporting quirk to paper over.  It affects `artifacts.digest`,
   `attempts.attempt_id`, `claims.wo_id`, `schema_migrations.version`,
   `sessions.session_id`, `wo_state.wo_id`, `work_orders.wo_id`.  The two
   composite-PK tables differ: `events` and `gate_kinds` declare their key
   columns `NOT NULL` explicitly, so they report `notnull: true`.  A contract
   asserting "pk implies notnull" will fail on seven tables, and the SQL is
   what it is.

4. **`migrations/*.sql` and `wf.db` agree exactly.**  `schema.facts.tables`
   and `db.facts.tables` are equal element for element — the same nine tables
   with the same columns, types, notnull flags and primary keys.  The
   migration file's sha256
   (`6cef53631d100a66…`) is also what `schema_migrations.sha256` holds, so the
   recorded digest matches the file that is on disk.  This is the one
   cross-observation check in 5.1/5.2 that comes out clean.

5. **48 tracked files, where SCOPE says 49.**  `layout.facts.files` lists 49
   entries, of which one is the untracked `wf.db` — so 48 tracked.  The
   difference is `PLAN.md`, which SCOPE names as living at
   `ops/devlane/workflow/PLAN.md` and which is deliberately absent from this
   snapshot.  `INVENTORY.txt`, also named by SCOPE, is likewise absent.  No
   extractor reads or needs either.

6. **`meta.json` carries a commit identity, including an email address.**
   `raw.commit_identity` holds a name and a GitHub noreply address.  It is in
   the tracked file, so it lands verbatim in `obs/meta.json` and in the
   provenance `text` for all four `meta` facts.  Nothing was redacted —
   provenance must be verbatim — but a contract author constraining `raw`
   should know the object has a second top-level key besides
   `format_version`, and a closed `#Meta.facts.raw` will surface it.

7. **No `.git` directory, and no `.gitignore` anywhere.**  See the 5.5 GUESS
   above.  `layout`'s repo-root resolution therefore never finds a `.git`
   marker and falls back to the `.dev/` parent, which it says in provenance.

8. **The `sessions` table holds one row and `attempts`, `events`, `wo_state`,
   `artifacts`, `claims`, `work_orders` are empty.**  Only
   `work_orders_count` is in the 5.2 shape, so the other counts are not
   emitted; `provenance.tables_present` lists the nine table names.  SCOPE's
   description of the database ("two gate kinds, one session, one migration
   row, and no work orders") matches what is there.

## `vet.py` (SPEC section 6)

Implements steps 1–6.  Three things about it need saying, because each is a
place where the command decides something section 6 left to the implementer.

**Sections 9 and 10 of the plan are not in the SPEC excerpt this was written
against.**  Step 3 says packets follow section 9, step 4 says verdicts are
validated per section 9, and step 5 says findings draw on section 10.  None of
those texts is available.  So `vet.py` implements exactly the three verdict
properties step 4 *names verbatim* — the enum is one of `doc-wrong` /
`code-wrong` / `ambiguous` (step 5 supplies those three values), `citations` is
required and non-empty, and every `quote` must appear verbatim in the packet —
and emits `REPORT.section_9`, `REPORT.section_10` and a section of
`FINDINGS.md` as explicit `{"unresolved": …}` markers rather than inventing the
rest.  Packets are laid out to be useful (error, observed value, provenance
with verbatim source, the cited contract lines, and what a verdict must
contain) and each one says in its own text that section 9 was unavailable.

**The determinism check runs by default.**  Section 6 makes
`--check-determinism` a flag, but step 6 lists "determinism holds" as one of
the four conditions for exit 0.  A flag that was not passed would leave that
condition unchecked while the command still exited 0, which is the vacuous
pass the whole plan is built to avoid.  So the check is on unless
`--no-check-determinism` is passed, and passing it records
`{"unresolved": …}` and fails the gate.  Two other decisions follow the same
rule: **zero contracts is a failure**, not a clean sweep, and a fault whose
`reject_path` only matches lines the clean run already emits fails
`attributable_to_fault` even though `cue vet` exited non-zero.

**A skipped `db` observation is a recorded skip, not a failure.**  5.2 says
the observation is "skipped when the file is absent (REPORT says so)", so when
`wf.db` is missing `vet.py` skips the extractor, notes it in
`REPORT.steps.extract.skipped`, still runs `cue/db.cue` against
`examples/db.json` (the positive control does not depend on the observation),
and records that the faults could not be measured.  It does not pretend the
observation passed.

Packet ids are `<name>-<sha256(error path)[:8]>` as step 2b specifies.  "Error
path" is defined here as the CUE path prefix before the first `": "` on a
non-indented `cue vet` stderr line — e.g. `facts.bytes` from
`facts.bytes: invalid value 112 (out of bound <100):`.  A stderr line with no
path prefix hashes the whole line instead.  Indented lines are the error's
source locations and are attached to it, not hashed.

`vet.py` was exercised against a throwaway contract outside `contracts/`
(`/tmp/vettest`, not part of any deliverable) to confirm every branch fires:
example pass and example absent; observation pass and observation mismatch;
packet written and verdict absent; verdict with a bad enum; verdict with an
empty `citations`; verdict whose `quote` is not in the packet; a valid verdict
closing the gate; a fault that does not differ from the observation; a fault
with an incomplete sidecar; only one fault present; a fault whose
`reject_path` matches only a pre-existing clean-run line; a contract name
outside section 4's fixed map; `wf.db` absent with `cue/db.cue` present; and
`--no-check-determinism`.  Each failed as intended and each message named what
was missing.

## Author B — cli, exitcodes, canonical, events, commitmsg, mcp, vocab

# EXTRACTION-NOTES — extractors for SPEC §5.6–§5.12

Author: extractor author (B). Scope: `extract/cli.py`, `extract/exitcodes.py`,
`extract/canonical.py`, `extract/events.py`, `extract/commitmsg.py`,
`extract/mcp.py`, `extract/vocab.py`.

The plan document these modules were built from (`PLAN.md`) is **not in this
snapshot**. Nothing here is reconstructed from it, inferred from it, or
shaped to agree with it. Every fact below is what the source text says, with
the file, the line range and the verbatim lines carried in `provenance`.
Where a rule and the code disagree, the code is reported and the
disagreement is left for the contract to surface.

## How to run them

Each module is importable and exposes `NAME` and
`extract(app_dir=None) -> {"facts": …, "provenance": …}`. With no argument
the app directory is `Path(__file__).resolve().parents[2]`, i.e. the parent
of `contracts/`. Run standalone, `python3 extract/<name>.py [app_dir]` prints
the same object as `json.dumps(…, sort_keys=True, indent=2)`.

Stdlib only. No network. No module under inspection is imported or executed —
every file is read as text and parsed with `ast`.

## Conventions that apply to all seven

* **Provenance.** Every fact carries `{file, lines: "a-b", text, rule}`,
  `file` relative to `ops/devlane/workflow`, `text` the verbatim source lines of
  that range. Extra keys (`value`, `resolution`, `kind`, …) are free-form
  detail for the adjudicator.
* **Never vacuous.** A rule that cannot be resolved emits
  `{"unresolved": "<why>"}` in place of the value. Where a list *is* legitimately
  empty (see "Empty is not unresolved" below) provenance carries the evidence
  that makes the emptiness a finding rather than a default.
* **Determinism.** Lists are sorted; sets are never serialised directly; no
  timestamp, no absolute path, no machine-dependent value is emitted. Verified
  by repeated runs under different `PYTHONHASHSEED` (see the report).
* **String constants include f-string literal segments.** `ast.Constant` str
  nodes nested inside a `JoinedStr` are part of the population, flagged
  `kind: "f-string-segment"` in provenance and anchored to the f-string's line
  range. This matters for §5.10 and is noted per-GUESS below. Reconstructed
  f-string *templates* (`wf({wo_id}/{stage}): {summary}`) appear in provenance
  only; they are not string constants and are never mixed into a fact list.
* **Docstrings are string constants** and are scanned like any other.

# GUESS ledger — §5.6 to §5.12

Every line SPEC.md marks **GUESS** in those sections, with a verdict.
§5.8 (`canonical`) and §5.11 (`mcp`) carry no GUESS marker; that is recorded
below too so the absence is not read as an oversight.

## §5.6 `cli`

### G1 — "**GUESS**: argparse with literal strings" — **CONFIRMED**

`wf.py:1861-1983` `build_parser()` builds an `argparse` parser. Every
`add_parser` name and every `add_argument` option string and positional name
in it is a string literal; the extractor reports 17 commands with no
unresolved names.

One wrinkle the guess does not mention and the extractor handles: the root
parser is not `argparse.ArgumentParser` but `Parser`, a subclass declared at
`wf.py:1831-1833` that raises `Usage` instead of exiting. The extractor
collects module-level classes whose base is `argparse.ArgumentParser` and
treats them as parser constructors, and identifies the *root* as the parser
that `add_subparsers` is called on (`wf.py:1866`) rather than by name.

Not every `add_argument` keyword is literal — `--ttl` defaults to
`coord.DEFAULT_TTL` (`wf.py:1882`) — but `default` is not part of the §5.6
argument shape, so this changes no fact. A non-literal `action`, `nargs`,
`choices`, `required` or `dest` would be emitted as `{"unresolved"}`; none
occurs.

### G2 — "**GUESS**: common flags may be added by a helper function — follow one level, list the helper in `helpers_applied`" — **ADAPTED**

Adapted in the mechanism, and the guess's flag list is wrong in both
directions.

*The helper exists.* `common_options(parser, *, suppress)` at
`wf.py:1836-1858` adds five options to whichever parser it is handed:
`--root`, `--json`, `--agent`, `--source`, `--no-commit`.

*It is not called on the sub-parsers.* It is called twice: once on the root
parser (`wf.py:1863`) and once on a bare parent parser
(`common = argparse.ArgumentParser(add_help=False)`, `wf.py:1864-1865`) that
every `add_parser` then receives as `parents=[common]`. Following only "one
level of helper call" on each sub-parser would find nothing and every
command's `arguments` would be `{"unresolved"}` — a true statement about the
guess, and a useless observation. **Adaptation:** the extractor resolves
`parents=[…]` as well as direct helper calls. It tracks each parser variable
in `build_parser`, records which arguments reached it directly and which
through which helper, and when a sub-parser names a parent it copies that
parent's resolved arguments in and unions the parent's helper names into
`helpers_applied`. All 17 commands come back with
`helpers_applied: ["common_options"]` and the five inherited flags present.

*The guess's flag list is wrong twice.* `--root` is helper-added and is not
in the guess's list. `--allow-dirty` is in the guess's list but is **not**
helper-added: it is declared per-command on `red` (`wf.py:1905`), `green`
(`wf.py:1911`) and `check` (`wf.py:1949`) only, and appears on exactly those
three commands in the observation.

*Fallback preserved.* If a helper's body cannot be read (not a module-level
function, or no first parameter), the extractor emits `{"unresolved"}` for
that command's `arguments` and for `global_arguments`, exactly as the guess
requires. Exercised against a synthetic `wf.py`; it fires.

### G3 — "`next_json_keys`: **GUESS** — keys of dict literals inside the function the `next` command dispatches to" — **ADAPTED**

The dispatch half is confirmed: `wf.py:1893-1895` declares the `next`
sub-parser and `p.set_defaults(func=cmd_next)`, and the extractor resolves
the target from the `func=` keyword.

The dict-literal half, applied literally, is wrong. `cmd_next`
(`wf.py:450-474`) contains exactly one dict literal — `{"wo": None, "note":
"no open work orders"}` at `wf.py:460`, the *no work orders* early return.
The real payload is `body = summarise(ctx, row, projection)` followed by
`body.update(next_action(ctx, row, projection))` (`wf.py:466-467`), and both
of those are one-line delegates in `wf.py` (`wf.py:673-677`) to `query.py`
(`next_action` at `query.py:110-186`, `summarise` at `query.py:189-207`).
Emitting `["note", "wo"]` would be a confident wrong answer about what
`wf next --json` prints.

**Adaptation:** `next_json_keys` is the union of keys of every payload that
reaches `ctx.emit(<payload>, …)` inside the dispatch target, resolving

* dict literals (including `{**other}`, recursed into),
* a `Name`, through assignments to it, `.update(…)` on it, and
  `name["k"] = …` subscript assignment in the same function,
* a `Call`, one hop at a time into the callee's `return` expressions —
  same file for a bare name, and into a sibling module for `mod.fn` where
  `mod` is an `import` of a `<name>.py` that exists beside `wf.py`,

to a depth of 5, with a visited set. Result: 18 keys, and
`provenance.next_json_keys.unfollowed` is empty — no hop was abandoned. The
two-hop delegate chain is why one hop was not enough.

For every command other than `next`, `next_json_keys` is the literal string
`"n/a"`, per §5.6.

## §5.7 `exitcodes`

### G4 — "module-level `NAME = <int>` and class attributes, names containing EXIT or CODE — GUESS" — **ADAPTED**

Two adaptations, both recorded in `provenance.readings`.

**(a) The name filter is applied case-insensitively.** Spelled in capitals it
matches the six module constants of `errors.py:13-22` and *nothing else* —
the "and class attributes" half of the rule would be dead. Case-insensitively
it also matches the five `exit_code` class attributes at `errors.py:28, 44,
81, 111, 118`.

**(b) A class attribute whose value is a bare name is resolved** against the
module-level integer constants of the same file, because that is how all five
are written (`exit_code = EXIT_REFUSED`). The resolution
(`EXIT_REFUSED = 1, resolved against errors.py's module constants`) is in
provenance. A value that resolves to neither an int literal nor a
module-level int constant is emitted as
`{"name": …, "value": {"unresolved": …}, "file": …}` rather than dropped;
none occurs here.

Consequences worth stating plainly, since they change what the contract sees:

* `constants` holds 11 entries — 6 plain names, 5 spelled `Class.exit_code`.
  A contract that constrains `name` to `/^EXIT_/` will reject the dotted five.
  That is a real disagreement about the rule, not about the code.
* Class attributes add **no new value**: every one resolves to a code already
  present. `all_codes` is unchanged by adaptation (b).
* `True`/`False` are `int` in Python and are explicitly refused as exit codes.
* `CODE_DIR` at `wf.py:51` matches the name filter and is excluded because
  its value is not an int literal — the `= <int>` half of the rule does the
  work there, not the name half.

**`all_codes` is `[0, 1, 2, 3, 64, 70]`.** `EXIT_INTERNAL = 70` is declared at
`errors.py:22` under a comment saying it is outside the plan's map on
purpose, and `wf.py:8-18` and `wf.py:2013-2022` say the same. This is emitted
as observed. If the contract requires exactly `{0,1,2,3,64}` the mismatch is
real and belongs in a verdict.

## §5.8 `canonical` — no GUESS in this section

Recorded so the absence is deliberate: §5.8 marks nothing GUESS, and the
extractor needed no adaptation. `canonical.py:35` is the single
`json.dumps` call; its keywords come out as
`{"sort_keys": true, "separators": [",", ":"], "allow_nan": false}` and
`hashlib_algorithms` as `["sha256"]` from `canonical.py:52`.

Two mechanical choices, in `provenance.readings`:

* a tuple literal is rendered as a JSON array (JSON has no tuple), so
  `separators=(",", ":")` reads `[",", ":"]`; the verbatim source and the
  unparsed keyword (`(',', ':')`) are both in provenance;
* a keyword whose value is not a literal would be the string `"non-literal"`,
  exactly as §5.8 spells it; none occurs.

The `allow_nan=False` keyword is present in the code and absent from the
canonical-form definition §5.8 quotes. Whether that breaks byte-identity is
the contract author's reading to record; the extractor only reports that the
keyword is there.

## §5.9 `events`

### G5 — "GUESS: event types are dotted literals; the regex also catches filenames" — **CONFIRMED, with one miss the guess does not predict**

The mechanism holds: `chain.py:35-44` declares the event types as dotted
lowercase string constants and the regex finds them. The predicted noise is
real — of the 12 values observed, `meta.json`, `wf.db` and `wf.py` are
filenames, not event types.

The miss: `chain.py:40` is `OUTCOME = "outcome"`, an event type **with no
dot**, so `/^[a-z]+\.[a-z_]+$/` cannot see it. It does not appear in `types`.
It *does* appear in `shapes` (`wf.py:1179`, resolved through
`chainmod.OUTCOME`), so the two facts of this observation disagree with each
other — visibly, which is the point. If the documented type set includes
`outcome`, the contract's `documented ⊆ observed` test fails on that one
value and the correct verdict is against the extraction rule, not the code.

`types[].files` is populated per distinct value; the file population is
`provenance.files` (18 files: every `*.py` under `ops/devlane/workflow` minus
`tests/`, `contracts/`, `__pycache__/` and anything named `test_*.py`).

### G6 — "GUESS: dict literals containing key `type` whose value is a string constant; keys = its literal keys plus subscript-assigned keys on the same name in the same function" — **ADAPTED**

Applied literally the rule sees almost none of this app's event
construction. Every chain append writes the type through a constant from
another module — `ctx.chain.append(wo_id, {"type": chainmod.WO_OPENED, …})`
at `wf.py:400` — which is an `Attribute`, not a string constant. What
survived the literal rule would be 17 fragments of `mcp_server.py`'s MCP
plumbing and not one event.

**Adaptation:** a `"type"` value is accepted when it is a string constant, or
when it is a `Name`/`Attribute` that resolves to a module-level string
constant of the same file or of a sibling module imported by it (aliases
followed: `import chain as chainmod` → `chain.py`). The resolution is
recorded per shape in `provenance.shapes[].type_resolution`, e.g.
`chainmod.WO_OPENED = 'wo.opened' at chain.py:35`.

**Second adaptation — unresolvable types are kept, not dropped.** A dict with
a `"type"` key whose value resolves to no string is emitted with
`type: {"unresolved": …}` and its keys intact. Dropping them would hide the
single most important shape in the app: the receipt body at `wf.py:837-858`
has 20 keys and its `"type"` is the `etype` *parameter* of
`receipt_event(...)`, so no AST-local rule can name it. The other four are
`wf.py:1800` (marker, also an `etype` parameter), `wf.py:501` and
`query.py:308` (`e.get("type")` projections, not event constructors) and
`mcp_server.py:263` (a JSON-Schema property that happens to be *named*
`type`). Five of 28 shapes; each one's reason is in the emitted string.

**Noise the rule genuinely produces:** 18 of the 28 shapes come from
`mcp_server.py` — `{"type": "object"|"string"|"array"|…}` fragments of the
MCP tool schemas at `:235-292`, plus the two JSON-RPC content blocks
`{"type": "text", "text": …}` at `:388` and `:392`. They match the rule
exactly; they are not events. The 10 that are event constructions are all in
`wf.py` and `query.py`.

**`keys` is a lower bound where the source is open-ended.** Two flags in
provenance say so: `open_keys` for `{**expansion}` inside the dict, and
`updates` for `.update(…)` calls on the bound name — e.g.
`body.update(extra or {})` at `wf.py:859` means the receipt shape can carry
keys no AST can enumerate. `keys` is sorted; the subscript half of the rule
is implemented (assignments `name["k"] = …` in the same function) and fires
nowhere in this tree.

## §5.10 `commitmsg`

### G7 — "trailer_keys: from string constants matching `/^[A-Z][A-Za-z-]*:/` — GUESS" — **ADAPTED**

The commit message is built at `gitio.py:224-245`. Of its seven message
lines exactly one is a plain string constant — `"Source: generated: wf"` at
`gitio.py:239`. The other six are f-strings: `f"WO: {wo_id}"`,
`f"Stage: {stage}"`, `f"Event: {seq} {head[:8]}"`, `f"Source: {source}"`,
`f"Co-Authored-By: {agent}"`.

Under the unadapted reading (top-level `ast.Constant` only) `trailer_keys`
would be `["Source"]` — a confident, wrong answer that four trailers do not
exist. **Adaptation:** the string-constant population includes `ast.Constant`
str nodes nested inside a `JoinedStr`, each flagged
`kind: "f-string-segment"` and anchored to the f-string's line range, with
the reconstructed template beside it. `trailer_keys` is then
`["Co-Authored-By", "Event", "Source", "Stage", "WO"]`.

### G8 — "subject_literals: string constants containing `wf(` — GUESS" — **CONFIRMED, and thin**

The subject is `f"wf({wo_id}/{stage}): {summary}"` at `gitio.py:233`. Its only
literal segment containing `wf(` is `"wf("` itself, so
`subject_literals == ["wf("]`. The rule is confirmed — there is exactly one
such literal and it is the subject line — but the fact carries almost no
shape. The reconstructed template `wf({wo_id}/{stage}): {summary}` is in
`provenance.subject_literals[].fstring_template` and deliberately **not** in
the fact list, because §5.10 says "string constants" and a template is not
one. A contract that requires a subject literal matching
`^wf\(.*\): ` will fail against `"wf("`; the verbatim source line is in
provenance for the adjudicator.

`literals` (no GUESS marker) is the same population filtered on `":"`, nine
values, including two docstrings that contain a colon.

## §5.12 `vocab`

### G9 — "**GUESS**: terms may be encoded as a regex (e.g. `work[ -]order`)" — **CONFIRMED as not happening here**

`checks/vocabulary_wall.py:31-36` lists `RESERVED` as 19 plain string
constants — `"work order"`, `"work orders"`, `"gate"`, `"gates"`, … The regex
is built *around* each term at line 50
(`rf"(?<![\w-]){re.escape(term)}(?![\w-])"`, and `re.escape` proves the term
is meant to be literal text); the terms themselves are never regex source.
So the substring test §5.12 describes is testable as written.

Two facts about the observation that bear on that test, reported without any
claim about what the plan says (this snapshot has no `PLAN.md`):

* `literals` includes the module docstring (`:2-20`), which itself names the
  reserved vocabulary in prose. A term can therefore be a substring of
  `joined` via the docstring even if `RESERVED` does not list it.
* `RESERVED` spells two terms as `"red stage"` and `"green stage"` where the
  docstring says `red/green`. Bare `red` and `green` are still substrings of
  `joined` (through `"red stage"`, `"green stage"`), so the substring test
  cannot distinguish the two spellings. If the contract needs word-boundary
  equality rather than substring, that is a contract-side decision and this
  observation supports either.

`joined` is `"\n".join(literals)` over the **sorted unique** list, so a term
that spans two adjacent literals in source order is not a substring of it.

# Surprises — things in the code the §5 shapes do not fit

Recorded here because a shape that does not fit is a finding, not a bug to
paper over.

1. **`wf.py` declares 17 verbs, and §5.11's fixed §4 verb list has 16.** The
   extra is `agents` (`wf.py:1979-1981`, "per-agent projection over what is
   recorded"). §5.6 says §4's table is exact, not a subset. Either the table
   omits `agents` or the verb is undocumented; either way it is a real
   disagreement and neither extractor invented it. `agents` is absent from
   §5.11's list too, which is why `verb_literals` is three values and not
   four — `"agents"` occurs twice as a string constant in `mcp_server.py`
   (`:177`, `:211`) but is not in the list the rule fixes.

2. **Exit code 70 exists and is deliberate.** `errors.py:19-22` and
   `wf.py:8-18` both explain why it sits outside the documented map. §5.7
   says the set is exactly `{0,1,2,3,64}`. The observation says otherwise and
   says why, verbatim, in provenance.

3. **`outcome` is an event type with no dot** (`chain.py:40`), which §5.9's
   regex structurally cannot see. See G5.

4. **The §5.9 shapes rule matches JSON Schema.** 18 of the 28 shapes come
   from `mcp_server.py` — MCP tool-schema fragments (`:235-292`) and JSON-RPC
   content blocks (`:388`, `:392`). Nothing distinguishes them from an event
   dict at the AST level, so they are reported.

5. **`--json` is both global and per-command.** `common_options` is called on
   the root parser *and* on the `parents=` parent (`wf.py:1863-1865`), with
   `argparse.SUPPRESS` defaults on the second so a flag given after the verb
   does not overwrite one given before it (`wf.py:1836-1845`). §5.6 says the
   contract "accepts either by checking `global_arguments` first" — the
   observation shows both, with identical option strings and different
   defaults. Defaults are not in the §5.6 shape, so the difference is
   invisible in `facts` and visible only in the provenance `text`.

6. **§5.6's argument shape has no `type` field**, so `type=int` on
   `-n/--number` (`wf.py:1970`) is not observable. Same for `metavar` on
   `check`'s `target` (`wf.py:1943`) and for `dest` on per-command arguments
   — `--recorded-by` sets `dest="recorded_by"` (`wf.py:1967`) and the shape
   only carries `dest` for globals. All three are in the provenance `text`.

7. **The receipt event shape has no statically knowable type.**
   `receipt_event` (`wf.py:832-860`) takes `etype` as a parameter and ends
   with `body.update(extra or {})`. §5.9's shape assumes both the type and the
   key set are determinable at the construction site; here neither fully is.
   Reported as an unresolved type with a 20-key lower bound.

8. **`arguments` is sorted, not in declaration order.** §5.6 does not say
   which, and §4's determinism rule says "sorted lists only" (§5.1 grants
   declaration order explicitly, §5.6 does not). Sort key: the positional
   name, else the first option string. Source order and line numbers are
   preserved in `provenance.commands.<name>.arguments`.

9. **`mcp_server.py` imports `chain` and `store`.** §5.11 says the contract
   draws on "imports the query layer, not the append layer" and flags the
   ambiguity of "append layer" itself. The observation just lists the eight
   local imports; which of them count as the append layer is the contract
   author's reading to record, not the extractor's.
